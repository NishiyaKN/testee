Questões reais: quiz nº 20 · slides Q2

  • Herança modela "é-um": a subclasse precisa ser um subtipo que substitui a base sem quebrar o comportamento esperado (Princípio de Substituição de Liskov, LSP).
  • Composição/delegação modela "tem-um" ou "usa": a classe guarda uma referência e delega.
  • Nunca herde só para reaproveitar código: "prefira composição à herança" (Effective Java, item 18; GoF).

Caso típico: SensorTemperaturaSmart extends ComunicadorRede só para usar enviarPacote(). O sensor não é um comunicador, ele usa a rede. A herança expõe estabelecerConexao() e enviarPacote() a qualquer cliente do sensor, pode quebrar a substituibilidade e acopla rigidamente (trocar a rede por Bluetooth quebra a hierarquia). Já implements DispositivoAtuador está certo: a interface é um contrato sem estado. Correção: o sensor guarda um canal de rede (que ComunicadorRede pode implementar) e delega a ele.

class SensorTemperaturaSmart
    implements DispositivoAtuador {
  // composição: o sensor USA um canal
  private final CanalComunicacao canal;
  private double temperaturaAtual;
  SensorTemperaturaSmart(
      CanalComunicacao c) {
    canal = c;  // injetado
  }
  public void acionarAlerta(String m) {
    if (temperaturaAtual > 40.0)
      canal.enviarPacote(m.getBytes());
  }
}

Prefira composição quando a especialização não é estável, o reúso é só de código, a base expõe detalhes protected ou as capacidades se combinam de forma independente. Use herança numa hierarquia pequena, coesa e documentada como contrato de substituição.

Distratores típicos:
  • "Interfaces servem para simular herança múltipla de estado": interface não tem estado de instância.
  • "A herança está certa (especialização); a falha é a interface, que impede o reúso": aceita um "é-um" falso. Interface define contrato, não serve para reúso de código.
  • "Herdar evita duplicação e compensa a falta de herança múltipla": reúso não justifica herança, e Java já tem herança múltipla de tipo por interfaces.

Field shadowing: se a subclasse redeclara um campo com o mesmo nome, o objeto passa a ter dois campos. Nada é realocado: o novo campo só oculta o antigo, e o código da superclasse continua lendo o dela.

Template Method (comportamental, GoF): a superclasse define o esqueleto do algoritmo (processar) e as subclasses implementam passos (taxa).

abstract class Base {
  protected double fator = 1.5;
  double processar(double v) {
    // lê Base.fator (estático)
    return v * fator + taxa();
  }
  protected double taxa() {
    return 10.0;
  }
}
class Sub extends Base {
  // 2º campo: só oculta o 1º
  protected double fator = 2.0;
  @Override
  protected double taxa() {
    return 25.0;  // dinâmico
  }
}
Base p = new Sub();
p.processar(100.0);
// 100 × 1.5 + 25 = 175.0
SuposiçãoContaSaída
Campo estático, método dinâmico (correto)100 × 1.5 + 25175.0
Campo também "polimórfico"100 × 2.0 + 25225.0 ✗
Tipo da referência fixa tudo (sem despacho)100 × 1.5 + 10160.0 ✗
Atributo → estático. Método sobrescrito → dinâmico. Com Sub p = new Sub() continua 175.0 (o campo é lido dentro de Base). Sem redeclarar o campo e com super(2.0) no construtor, ou com um getFator() sobrescrito: 225.0. Com taxa() private ou static: 160.0.

Projeto: o shadowing é falha (dois estados com o mesmo nome, quebra do encapsulamento). Configure o estado herdado por construtor ou por método polimórfico.

"225.0 e alta coesão" supõe atributo polimórfico e elogia o shadowing. "160.0 e projeto seguro" ignora o @Override: o tipo declarado não impede o despacho de métodos. "A subclasse redefine a alocação de memória do atributo": nada é realocado. O slide diz "tipo DECLARADO da referência". O exato é o tipo estático onde o campo é lido.

  • Sintoma: um if / else if por modalidade que cresce a cada regra nova. Toda nova regra obriga a editar a mesma classe, o que viola o OCP (aberto para extensão, fechado para modificação) e reduz a coesão.
  • Strategy (comportamental): uma interface comum e uma classe por algoritmo. O contexto recebe a estratégia por composição/injeção. Nova modalidade = nova classe, sem tocar no código existente.

Singleton não remove if nem melhora a coesão, e ainda cria estado global. Nuance: o Strategy tira os if do contexto, mas a escolha da estratégia ainda acontece em algum lugar (injeção, Map).
  • Classe = tipo/descrição (atributos, operações, construtores, regras de acesso). Objeto = instância com identidade (distingue objetos de valores iguais), estado (valores no momento) e comportamento. Não são sinônimos.
  • Pré-condição: o que o cliente garante antes da chamada. Pós-condição: o que a operação garante depois. Invariante: vale em todo estado observável.

Dois default iguais vindos de interfaces não relacionadas causam erro de compilação até a classe sobrescrever. Java não escolhe pela ordem do implements. Dois métodos abstratos iguais não conflitam.

"Java não tem herança múltipla" é frase incompleta: tem herança múltipla de tipo (interfaces), mas não de estado/implementação de classes. C++ aceita várias classes-base (bases virtuais no diamante). Python usa a MRO C3.

  • final na referência só impede reatribuir: o ArrayList continua mutável. private protege o nome do campo, não o objeto devolvido. Método final só impede sobrescrita.
  • Correção: return List.copyOf(alunos); (um add lança UnsupportedOperationException) e alterações só por operações de domínio. A cópia não torna os elementos imutáveis nem resolve concorrência.
  • Herança pode ser de tipo, de implementação ou de estado. Subclasse ≠ subtipo: só é subtipo se puder substituir a base sem quebrar expectativas documentadas.
  • Construtores não são herdados. A subclasse inicializa a base com super(...), obrigatório quando a base não tem construtor sem parâmetros (Circulo chama super(cor)).
  • @Override faz o compilador acusar erro se a assinatura não sobrescrever nada. Sem ele, area(int) viraria uma sobrecarga silenciosa.
  • LSP: o subtipo não pode exigir pré-condição mais forte, entregar pós-condição mais fraca ou lançar exceção para entradas que a base aceita.     return "Base"; }
  String tipo() { return "Base"; }
}
class Derivada extends Base {
  static String nome() {
    return "Derivada"; }
  @Override String tipo() {
    return "Derivada"; }

// sobrecargas: imprimir(Base b)
//          e imprimir(Derivada d)

O GoF reúne 23 padrões em 3 grupos: criacionais, estruturais e comportamentais (veja a tabela). Padrão não é biblioteca, framework nem receita, e todo padrão tem custo. Descreva o problema sem o nome do padrão:

  • Colegas conhecidos que se referenciam (campos e botão de uma tela) → Mediator.
  • Receptores variáveis de um evento (cache, interface, auditoria) → Observer.
  • Configuração única que precisa de testes isolados → instância única criada na composição e injetada.
  • Fórmula fixa, usada num ponto só, sem variação → chamada direta, sem padrão.
  • Observer: dependência 1→N. O publicador (ProductCatalog) conhece só a interface (PriceObserver). Os observadores se inscrevem e cancelam em execução.
  • Notifique percorrendo List.copyOf(observers): um cancelamento durante a notificação não afeta a iteração corrente e vale para os próximos eventos. Sem a cópia, um observador pode ser pulado em silêncio.
  • Observer não garante, por si só, ordem, entrega exatamente uma vez, persistência ou transação. java.util.Observable está depreciada desde o Java 9.
  • Mediator: cada componente só avisa o mediador (mediator.notify(this, "click")) e não conhece os colegas. O RegistrationDialog decide quem reage, e um campo novo altera só o mediador. Custo: o mediador crescer demais (God Object). Mitigue dividindo por contexto, usando eventos tipados e delegando regras de domínio.
Mediator não é Facade (que simplifica a interface de um subsistema). Usar Observer com todos inscritos em todos mantém o acoplamento N×N. Mediator coordena colegas conhecidos; Observer notifica receptores que variam.
public final class AppConfig {
  private AppConfig() {}
  private static class Holder {
    static final AppConfig INSTANCE =
        new AppConfig();
  }
  static AppConfig getInstance() {
    return Holder.INSTANCE;
  }
}
  • Criacional: construtor privado + acesso estático. A JVM inicializa Holder uma vez, de forma sincronizada, na 1ª chamada a getInstance(). A criação é tardia e segura entre threads, sem synchronized. Um enum também serve.
  • A unicidade vale só no escopo: não vale entre JVMs, class loaders ou processos, e a reflexão pode criar outra instância.
  • Custo: acesso global (dependências ocultas, estado entre testes, dublês difíceis). Prefira uma instância criada na composição da aplicação e injetada: new Service(logger). Só use Singleton se instâncias extras causarem dano real.
